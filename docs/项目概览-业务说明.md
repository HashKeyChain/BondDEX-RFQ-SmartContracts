# BondDEX RFQ 智能合约 — 业务概览

本文面向**产品、运营、合规、法务、商务**等非技术同事，用业务语言说明：**这套系统在链上负责什么、各功能如何衔接**。不涉及实现细节与工程术语。

---

## 一、项目是做什么的

BondDEX RFQ 的链上部分解决三件事：

1. **债券数字化**：每支债券在链上对应一份可转让的债权凭证，条款（面值、票息、到期日、结算币种）在发行时确定，之后不可篡改。
2. **一级市场认购**：发行人在约定窗口内开放认购，**做市商**用结算资产换得债权凭证，再通过二级市场向投资者分销。
3. **二级市场交易（RFQ）**：做市商与投资者通过「报价 → 确认成交」在链上完成原子交割，系统确保**只有合规参与方、在允许的方向上**才能过户。

简单理解：**一本不可单方面抵赖的账本 + 一套自动执行的交割与合规规则**。界面、风控审批、KYC 资料收集在链下完成，链上记录最终结果。

## 二、主要参与方

| 角色 | 在业务里的位置 |
|------|----------------|
| **平台 / 治理方** | 审批谁能发哪支债、配置全局规则（手续费、允许的结算币等）、紧急时按业务环节暂停部分能力；重要操作由多签钱包共同确认，避免单人擅权。 |
| **发行人** | 发起债券、开放认购、到期前准备赎回资金；对自己发行的债券负有对应义务。 |
| **做市商** | 在一级市场完成认购并获得债权凭证；在二级市场提供流动性，与投资者或其他做市商按约定规则成交。做市商承担二级市场交易中的手续费。 |
| **投资者** | 通过二级市场从做市商处购买或向做市商出售债权凭证；持有债券并在到期后领取赎回款。投资者不承担手续费。 |

## 三、功能是如何串起来的（当前已落地的能力）

下面按**用户能感知到的业务流程**说明，对应关系是「业务动作 → 链上在做什么（概念上）」。

### 1. 创建一支债券

- **业务含义**：**平台批准某次发行后**，系统为这支债**单独**生成：债权凭证 + 专属于该债的合规配置。
- **效果**：每支债互相隔离；一支债的合规名单、角色、暂停状态不会影响另一支债。

### 2. 谁可以参与（合规与角色）

- **业务含义**：每个链上地址会被标记为：是否在白名单、是发行人 / 做市商 / 投资者中的哪一种。
- **准入规则**：未准入的地址无法完成认购和交易。
- **交易方向限制**：
  - **做市商 ↔ 投资者**：允许 — 这是最常见的交易方向
  - **做市商 ↔ 做市商**：允许 — 做市商之间可以互相交易
  - **投资者 ↔ 投资者**：禁止 — 以减少规避监管或转让限制的路径

### 3. 一级市场：认购

- **业务含义**：发行人打开认购窗口，约定价格、额度、时间等；**做市商**用约定的结算资产（如 USDC）支付，系统**记账并发放**对应数量的债权凭证。
- **效果**：认购与发放在同一套规则下自动完成；若窗口未开、额度已满、或参与者不合规，则无法完成。
- **为什么是做市商认购**：做市商扮演"承销商"角色，先在一级市场获取债权凭证，再通过二级市场向投资者分销。这符合传统债券市场中承销商/一级交易商的运作模式。

### 4. 二级市场：RFQ 成交

- **业务含义**：做市商在链下给出报价并留下「可验证的承诺」（可理解为带签名的成交条件）；对手方在链上**主动发起成交**时，系统核对承诺真伪、双方身份与合规状态，然后**同时**完成：债权凭证与结算资产的交换（原子交割）。
- **效果**：避免「先打款后收不到券」或「先过户收不到款」的单边风险。
- **批量成交**：支持一次提交多笔订单并原子化执行，要么全部成交、要么全部不成交。

#### 手续费规则

二级市场的手续费**始终由做市商侧承担**，投资者不受影响：

| 场景 | 资金流示例（以 30 bps = 0.3% 为例） |
|------|------|
| 做市商卖出债券 / 投资者买入 | 投资者付 10,000 → 做市商到手 9,970 → 平台收 30 |
| 做市商买入债券 / 投资者卖出 | 做市商付 10,030 → 投资者到手 10,000 → 平台收 30 |
| 做市商之间交易 | 做市商 B 付 10,000 → 做市商 A 到手 10,000 → 平台不收费 |

系统还提供**手续费预估查询**（`quoteFee`），做市商可在报价前调用来精确计算需要承担的费用。

#### 订单管理

- **订单取消**：做市商可以随时取消尚未成交的订单
- **批量取消**：支持一次性取消多笔订单
- **Nonce 递增**：可以一键使所有历史报价失效，适用于行情剧烈波动时快速撤价

### 5. 到期与赎回

- **业务含义**：债券到期后，发行人向系统注入约定用于赎回的资金（面值 + 票息）；**任何持有债权凭证的人**（无论是做市商还是投资者）按规则**销毁**手中的凭证并**领取**对应结算资产。
- **代理领取**：持有人可以授权一个代理人帮自己领取赎回款，赎回资金始终打给持有人本人，代理人只负责触发操作。
- **效果**：赎回路径与认购、交易一样，受同一套合规与暂停策略约束。

### 6. 运营与风控：分域暂停

- **业务含义**：平台可按**不同业务环节**单独暂停，而不一定要「全盘关停」。
- **可独立暂停的环节**：
  - 债券创建（工厂）
  - 一级认购
  - 二级市场结算
  - 合规管理操作
  - 赎回资金注入
  - 到期领取
- **效果**：出事时缩小影响面，便于排查与恢复。例如发现二级市场异常时，可以只暂停交易结算，而不影响一级认购和赎回领取。

### 7. 升级与权限交接

- **可升级**：认购模块、结算模块和每债的合规模块可在**不改变合约地址**的前提下升级逻辑，但升级权限由多签掌握。
- **权限交接**：部署完成后，系统自动将各角色授予配置的多签地址，并**选择性撤销**部署者权限——已经移交给多签的角色自动放弃，部署者仍需暂时持有的角色保留并记录，确保不会出现「角色无人持有」导致功能锁死的情况。
- **效果**：安全与迭代兼顾；重要变更须多人批准，无单点私钥风险。

## 四、合规升级路线（规划中）

当前系统已具备完整的业务能力，后续规划在此基础上**增强合规与身份管理**：

- **目标**：采用行业通行的证券型代币标准（ERC-3643），将 KYC 身份、监管动作（冻结、强制划转、资产找回）纳入标准化、可审计的框架。
- **关键变化**：
  - **全局身份注册**：参与者一次完成身份关联后可交易多支债券，无需逐债重复准入。
  - **独立合规容器**：每支债券仍有独立的合规配置，但底层校验走统一标准。
  - **存量迁移**：平台在暂停旧通道后批量完成迁移，降低持有人操作负担。

业务视角：**产品流程（认购 → 交易 → 赎回）保持一致，监管能力与身份管理增强**，不影响已有业务逻辑。

## 五、链上系统**不**单独承担的部分（边界说明）

- **客户尽职调查、纸质材料、司法流程**：通常在链下完成；链上体现为「是否通过验证、是否具备某角色」等结果。
- **行情展示、聊天询价、订单簿**：RFQ 模式侧重「报价—确认成交」，深度与 UX 由应用层负责。
- **法币入金出金**：链上处理的是代币形式的结算资产（如 USDC）；银行通道由支付与托管体系完成。
- **手续费费率调整**：费率由平台治理方链上配置，但具体定价策略（收多少、何时调）是商业决策。

---

## 六、一句话总结

**BondDEX RFQ 把债券的发行审批、做市商认购、合规准入、二级 RFQ 原子交割（手续费由做市商承担、做市商间免费）、到期赎回、分域风控与权限交接，固化在链上自动执行的规则里；并规划在保留业务主线的前提下，升级到 ERC-3643 标准以支持机构级合规运营。**
