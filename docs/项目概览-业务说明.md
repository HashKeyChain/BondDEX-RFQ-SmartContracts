# BondDEX RFQ — 业务概览

本文面向**产品、运营、合规、法务、商务**等非技术同事，用业务语言说明：这套系统在链上负责什么、各参与方分别扮演什么角色、资金和债券如何流转、哪些数据不可变更、以及平台如何保障安全与合规。

---

## 一、这套系统解决什么问题

传统债券交易依赖多方人工对账、逐层清结算、纸质合同签署，效率低且存在单方违约风险。

BondDEX RFQ 将以下环节搬到区块链上自动执行：

1. **债券数字化**：每支债券对应一个链上「债权凭证」（类似电子化的债券证书），发行时写入面值、票息、到期日等条款，**一旦创建不可篡改**。
2. **一级市场认购**：发行人开放认购窗口，做市商用稳定币（如 USDC）支付后自动获得对应数量的债权凭证。
3. **二级市场交易（RFQ 询价模式）**：做市商报价、对手方确认，系统自动完成「一手交钱、一手交券」的原子交割——不存在先付款拿不到券、或先转券收不到款的风险。
4. **到期赎回**：债券到期后，发行人存入本金+利息，持有人销毁债权凭证领取赎回款。

简单理解：**一本不可单方面抵赖的电子账本 + 一套自动执行的交割与合规规则**。前端界面、风控审批、KYC 资料收集在链下完成，链上只记录最终结果。

## 二、参与方与角色说明

### 2.1 四类业务角色

| 角色 | 谁来担任 | 在业务中负责什么 |
|------|---------|---------------|
| **平台治理方** | 平台运营团队（通过多签钱包操作） | 审批哪些发行人可以发债、审批认购窗口、配置手续费和结算币种、管理合规白名单、紧急暂停、资金救援等全局管理工作 |
| **发行人** | 债券的发行机构 | 发起创建债券、开设认购窗口、到期前存入赎回资金（本金+利息） |
| **做市商** | 持牌做市机构 / 承销商 | 在一级市场认购债券（相当于传统的「承销」），在二级市场向投资者报价买卖，提供流动性 |
| **投资者** | 合格投资人 | 通过二级市场从做市商处买入或卖出债券，持有到期赎回 |

> **谁不能参与？** 没有被平台加入白名单的地址，无法进行任何操作——认购、交易、赎回全部会被拒绝。

### 2.2 平台治理方的细分权限

平台治理方并非一个人，而是一组**可独立配置**的权限角色，通常由不同的多签钱包持有：

| 权限角色 | 控制范围 | 典型持有者 |
|---------|---------|-----------|
| 管理员（Admin） | 管理其他角色的授予和撤销、紧急代币救援、释放超额赎回负债 | 核心治理多签 |
| 发行审批（Issuance Approver） | 审批/撤销债券发行申请、审批/撤销认购窗口申请 | 业务审批多签 |
| 合规管理（Compliance Admin） | 注册合规模板、管理白名单和角色分配 | 合规团队多签 |
| 结算管理（Settlement Admin） | 配置结算币种策略、手续费、应计利息容差、注册债券到二级市场 | 运营团队多签 |
| 暂停操作（Pauser） | 按业务环节独立暂停/恢复 | 风控 / 安全团队 |
| 升级操作（Upgrader） | 升级可升级合约的逻辑（修复漏洞或新增功能） | 技术团队多签 |

> **为什么要分这么细？** 传统金融中，审批、合规、运维、技术是不同团队。权限分离确保没有任何单人或单一多签能同时控制审批、资金和升级，降低内部风险。例如：审批团队能批准发债，但不能修改手续费；运维团队能调手续费，但不能批准发债。

### 2.3 每支债券的独立合规

每支债券发行时，系统会为它创建一个**专属的合规配置**（可以理解为该债券的「准入名册」）：

- **白名单**：只有加入白名单的地址才能参与该债券的认购和交易
- **角色标记**：每个地址只能有**一个角色**（发行人 / 做市商 / 投资者三选一），重新设置会覆盖旧角色
- **互相隔离**：A 债券的白名单和角色不影响 B 债券（从合约层面互相隔离）
- **独立暂停**：可以单独暂停某支债券的交易，不影响其他债券

这意味着：同一个做市商可以在 A 债券被授权交易，但在 B 债券未被授权——精确到**单支债券级别**的准入控制。

## 三、完整业务流程

下面用一个实际例子串联所有环节。假设 HashKey 平台要发行一支 1 年期公司债：

### 第一步：创建债券

```
平台审批 → 发行人创建 → 系统自动部署债权凭证 + 专属合规配置
```

**审批环节：**

1. **发行人**向平台提交发债申请（链下审批流程，如尽调、法律意见书等）
2. **平台审批人**在链上录入一条「发行审批」记录：
   - 允许哪个发行人地址创建债券
   - 使用哪个合规模板
   - 审批有效期（超过此期限未创建则审批自动失效）
   - 链下元数据引用（如 IPFS 哈希，关联尽调资料）

> **审批状态流转**：每个审批 ID 只能使用一次，状态单向流转，不可回退。待使用 → 已使用（创建了债券）/ 已撤销（平台主动取消）/ 已过期（超过有效期）。**无论进入哪个终态（已使用、已撤销、已过期），该审批 ID 都不能重新使用**。如需重新审批，必须用一个全新的审批 ID。认购审批同理。

**创建环节：**

3. **发行人**在链上创建债券，填入以下条款（**一经创建，永久不可修改**）：

| 条款 | 示例值 | 说明 | 创建后能否修改 |
|------|-------|------|:----------:|
| 名称 | HashKey Bond 2026 | 债券显示名称 | 不可修改 |
| 代号 | HKB-2026 | 债券缩写标识 | 不可修改 |
| 面值 | 1,000 USDC | 每份债券的面额 | 不可修改 |
| 年化票息 | 5%（500 基点） | 年化利率 | 不可修改 |
| 起息日 | 2026-01-09 | 利息从这天开始算 | 不可修改 |
| 到期日 | 2027-01-09 | 到期后可赎回 | 不可修改 |
| 计息惯例 | ACT/365 | 利息按实际天数/365 折算 | 不可修改 |
| 付息方式 | 到期一次付清 | 不分期，到期连本带利一起付 | 不可修改 |
| 债券类别 | 公司债 | 分类标识（公司债/政府债/可转债/ABS） | 不可修改 |
| ISIN | （可选） | 国际证券识别码 | 不可修改 |
| 结算币种 | USDC | 认购与赎回使用此币种；二级市场报价支持平台已启用的多种结算代币 | 不可修改 |
| 精度 | 0（整数） | 每份债券是一个不可分割的整数单位 | 不可修改 |
| 发行人地址 | 0x3C44... | 谁有权管理这支债券的认购和赎回 | 不可修改 |

4. 系统自动生成两样东西：
   - **债权凭证**（链上代币）：代表持有人对该债券的权利
   - **专属合规模块**：该债券自己的白名单、角色配置、暂停控制

> **为什么起息日设在认购结束后？** 确保所有认购者（无论谁先谁后认购）的利息起算点一致，不会因为认购时间不同导致利息差异。这与传统债券市场的「起息日」概念一致。

> **为什么条款不可修改？** 这些是投资者决策的基础。如果面值、票息、到期日可以事后修改，投资者的权益就没有保障。链上不可篡改正是用技术手段实现了「合同条款锁定」。

### 第二步：合规配置

```
[平台合规管理员]设置该债券的白名单和角色
```

| 操作 | 说明 | 可修改性 |
|------|------|---------|
| 添加/移除白名单 | 控制谁能参与该债券 | **随时可调整**（需合规管理员操作） |
| 设置角色 | 标记每个地址是做市商还是投资者 | **随时可调整** |
| 批量操作 | 支持一次性设置多个地址 | 同上 |

**这一步可以在债券存续期内随时调整**——比如新增一个做市商、移除一个不合规的投资者。

> **注意**：角色本身（做市商/投资者的区分）不决定白名单状态。一个地址可以被设为做市商角色但不在白名单中，此时仍然无法交易——**白名单是前置条件**。

### 第三步：一级认购

```
平台审批认购窗口 → 发行人开窗 → 做市商认购
```

**审批环节：**

1. **平台审批人**录入一条「认购审批」：
   - 允许该发行人、针对该债券、最多发行多少份
   - 审批有效期

> 与发行审批类似，每条认购审批只能使用一次，状态管理相同。

**开窗环节：**

2. **发行人**创建认购窗口：

| 设定项 | 示例值 | 创建后能否修改 |
|-------|-------|:----------:|
| 认购价格 | 1,000 USDC / 份 | 不可修改 |
| 最大发行量 | 1,000 份 | 不可修改（但不能超过审批上限） |
| 开始时间 | 2026-01-01 00:00 UTC | 不可修改 |
| 结束时间 | 2026-01-08 00:00 UTC | 不可修改（但发行人可提前关闭窗口） |

> 如果认购参数设置错误，发行人应先关闭当前窗口，重新申请审批后创建新的认购窗口。

**认购环节：**

3. **做市商**在窗口期内认购：
   - 做市商 A 认购 800 份 → 支付 800,000 USDC → 自动获得 800 份债权凭证
   - 做市商 B 想认购 500 份 → **被拒绝**（剩余只有 200 份）
   - 做市商 B 查询剩余额度 → 认购 200 份 → 支付 200,000 USDC → 获得 200 份
   - 做市商 C 想认购 → **被拒绝**（不在白名单中）

**资金流向：** 认购资金**直接从做市商转给发行人**，不留在合约中。债权凭证由系统直接铸造给做市商。

> **为什么只有做市商能认购？** 做市商相当于传统市场的「承销商 / 一级交易商」，先在一级市场获得债券，再通过二级市场分销给投资者。这符合传统债券市场中承销商/一级交易商的运作模式。

### 第四步：二级市场交易（RFQ）

```
做市商报价（链下签名）→ 对手方确认成交（链上执行）→ 原子交割
```

认购结束进入起息期后，债券持有人可以在二级市场交易。RFQ（Request for Quote，询价交易）是机构债券市场最常见的交易模式：买方向卖方询价，卖方给出报价，买方决定是否接受。

#### 完整的 RFQ 交易生命周期

**阶段一：询价与报价（链下）**

投资者想购买 10 份债券，在前端向做市商发起询价：

| 步骤 | 谁操作 | 做什么 | 在哪里 |
|------|-------|-------|-------|
| 1 | 投资者 | 在前端发起询价：「我想买 10 份 HKB-2026」 | 链下（前端 / 聊天） |
| 2 | 做市商 | 查看自己的持仓和市场行情，决定报价 | 链下 |
| 3 | 做市商 | 构造一份正式的「报价单」（订单），包含以下信息 | 链下 |

**报价单包含的信息：**

| 字段 | 示例值 | 说明 |
|------|-------|------|
| 报价方 | 做市商 A 的地址 | 谁在卖 |
| 接单方 | 投资者 A 的地址（或留空=任何人可接） | 谁能买 |
| 债券 | HKB-2026 的地址 | 哪支债券 |
| 结算币 | USDC 的地址 | 用什么付款（可使用平台已启用的任意结算代币，不限于债券创建时的币种） |
| 数量 | 10 份 | 买卖多少 |
| 报价金额 | 20,000 USDC（即每份 2,000 USDC） | 不含利息的价格（净价） |
| 应计利息 | 41.1 USDC | 起息至今累积的利息 |
| 方向 | 买入（从接单方视角） | 接单方买入债券 |
| 有效期 | 明天此时 | 超过这个时间自动作废 |
| 最高接受费率 | 1% | 做市商最多接受多少手续费 |

做市商用自己的私钥对这份报价单进行**数字签名**，签名后发送给投资者。

> **为什么要签名？** 签名相当于做市商的「不可抵赖的承诺」——只要报价单内容不变，签名就能证明确实是做市商本人给出的这个价格。做市商不能事后否认。

**阶段二：接单方决策（链下）**

| 步骤 | 谁操作 | 做什么 | 在哪里 |
|------|-------|-------|-------|
| 4 | 投资者 | 收到签名报价，核对价格、数量、应计利息 | 链下（前端） |
| 5 | 投资者 | 决定：接受 / 拒绝 / 等待再看 | 链下 |

投资者有三种选择：
- **接受**：进入阶段三，在链上成交
- **拒绝**：不做任何操作，报价到期自动作废
- **再询价**：向其他做市商询价，比较后选择最优

**阶段三：链上成交（原子交割）**

| 步骤 | 谁操作 | 做什么 | 在哪里 |
|------|-------|-------|-------|
| 6 | 投资者 | 将做市商签名的报价单提交到链上合约 | 链上 |
| 7 | 系统 | **逐项验证（全部通过才成交）** | 链上自动 |
| 8 | 系统 | 验证通过 → 同时完成资金和券的交换 | 链上自动 |

**系统在步骤 7 验证的内容（缺一不可）：**

| 验证项 | 验证内容 | 失败后果 |
|-------|---------|---------|
| 签名真伪 | 报价单确实是做市商本人签署的 | 交易拒绝，防止伪造报价 |
| 订单未成交 | 这份报价单没有被执行过 | 交易拒绝，防止重复成交 |
| 订单未取消 | 做市商没有撤回这份报价 | 交易拒绝 |
| 订单未过期 | 当前时间在有效期内 | 交易拒绝 |
| Nonce 有效 | 做市商没有一键作废过这批报价 | 交易拒绝 |
| 接单方身份 | 投资者是报价单指定的接单方（或报价单允许任何人） | 交易拒绝 |
| 双方白名单 | 做市商和投资者都在该债券的白名单中 | 交易拒绝 |
| 双方角色 | 符合交易方向限制（不能投资者对投资者） | 交易拒绝 |
| 债券已注册 | 该债券已在二级市场注册 | 交易拒绝 |
| 结算币已启用 | USDC 被允许用于二级结算 | 交易拒绝 |
| 应计利息合理 | 报价中的应计利息与链上计算值偏差在容差内 | 交易拒绝，防止篡改利息 |
| 手续费在范围内 | 当前费率不超过做市商签名时锁定的上限 | 交易拒绝，保护做市商 |
| 余额充足 | 投资者有足够 USDC，做市商有足够债权凭证 | 交易拒绝 |
| 授权充足 | 双方已授权合约转移对应资产 | 交易拒绝 |

**步骤 8 的资金流向（全部在同一笔交易中原子完成）：**

```
投资者支付：20,041.1 USDC（报价 20,000 + 应计利息 41.1）
  ├─ 做市商收到：19,980.98 USDC（全价 - 手续费 60.12）
  └─ 平台手续费：60.12 USDC（全价 × 0.3%）

做市商转出：10 份 HKB-2026 债权凭证
  └─ 投资者收到：10 份 HKB-2026 债权凭证
```

> **原子交割的含义**：上述资金划转和券的转移在同一笔交易中同时完成。如果任何一步失败（比如余额不足），整笔交易回滚，双方资产恢复原状——**不可能出现「钱付了但券没收到」或「券转了但钱没到账」的情况**。

**阶段四：交易后状态**

| 数据 | 交易前 | 交易后 |
|------|-------|-------|
| 做市商持有 HKB-2026 | 800 份 | 790 份 |
| 投资者持有 HKB-2026 | 0 份 | 10 份 |
| 做市商 USDC 余额 | 200,000 | 219,980.98 |
| 投资者 USDC 余额 | 1,000,000 | 979,958.9 |
| 该报价单状态 | 有效 | 已成交（不可再用） |

#### 其他交易场景

上面的例子是「投资者买入」。其他场景的流程相同，只是方向不同：

**投资者卖出债券给做市商：** 投资者持有 10 份，想卖给做市商。做市商签署一份「买入报价」，投资者确认后链上成交。资金方向反转：做市商支付 USDC + 手续费 → 投资者收到 USDC → 债权凭证从投资者转给做市商。

**做市商之间调仓：** 做市商 A 想把 100 份转给做市商 B。做市商 A 签署报价，做市商 B 接单。**免手续费**，但仍需支付报价金额 + 应计利息。

**批量成交：** 支持一次提交最多 24 笔订单，全部成功或全部失败（原子执行），适用于做市商一次性处理多笔报价。

#### 未成交订单的几种结局

| 结局 | 触发方式 | 说明 |
|------|---------|------|
| **成交** | 接单方在链上提交 | 正常完成，报价单标记为已消费 |
| **做市商取消** | 做市商主动调用取消 | 支持单笔或批量取消（上限 24 笔） |
| **自动过期** | 超过报价单中设定的有效期 | 无需任何人操作，链上自动拒绝过期订单 |
| **一键作废** | 做市商递增 Nonce Floor | 使所有历史报价一次性失效，适用于行情剧变时快速撤价 |

> **已取消 / 已过期 / 已作废的报价单不能再被成交**，链上会自动拒绝。

**交易方向限制：**

| 卖方 → 买方 | 是否允许 | 说明 |
|------------|---------|------|
| 做市商 → 投资者 | 允许 | 最常见场景：做市商向投资者分销 |
| 投资者 → 做市商 | 允许 | 投资者卖回给做市商 |
| 做市商 → 做市商 | 允许 | 做市商间调仓、头寸转移 |
| 投资者 → 投资者 | **禁止** | 防止绕过做市商的点对点转让，降低合规风险 |

**应计利息详解：**

债券从起息日开始每天产生利息。二级市场买卖时，买方除了支付约定的报价金额，还需向卖方补偿从起息日到成交日这段时间累积的利息——这就是「应计利息」。

举例：一支面值 1,000 USDC、年化 5% 的债券，起息 30 天后交易：
```
每份每日利息 = 1,000 × 5% / 365 ≈ 0.137 USDC
30 天应计利息 = 0.137 × 30 ≈ 4.11 USDC
买入 10 份的应计利息 ≈ 41.1 USDC
```

系统如何保证应计利息准确？
- 报价方在链下计算并填入订单
- 系统在链上用相同公式独立验算
- 如果两个值的偏差超过可配置的容差（默认 5 分钟对应的利息额度），交易被拒绝
- 这样既允许报价到成交之间几分钟的合理延迟，又防止恶意篡改

**三种计息惯例：**

| 惯例 | 计算方式 | 典型场景 |
|------|---------|---------|
| ACT/365 | 按实际天数除以 365 | 公司债、高收益债（本项目默认） |
| ACT/360 | 按实际天数除以 360（日利率略高） | 货币市场工具 |
| 30/360 | 每月按 30 天、全年 360 天 | 政府债、固定利率债 |

**手续费规则：**

| 交易场景 | 谁出手续费 | 计算基数 | 示例（费率 0.3%） |
|---------|-----------|---------|-------------------|
| 做市商卖 / 投资者买 | 做市商 | 报价 + 应计利息 | 投资者付 10,050 → 做市商到手 10,019.85 → 平台收 30.15 |
| 投资者卖 / 做市商买 | 做市商 | 报价 + 应计利息 | 做市商付 10,080.15 → 投资者到手 10,050 → 平台收 30.15 |
| 做市商 ↔ 做市商 | **免手续费** | — | 双方各收各付，平台不收费 |

> **手续费保护**：做市商签名时可锁定「我最多接受 X% 的费率」。如果平台在签名后、成交前调高了费率超过这个值，交易会被自动拒绝。这保护了做市商不会因为费率变动而蒙受意外损失。

> **手续费上限**：管理员可以调整当前费率，但不能超过部署时设定的费率上限（如上限 10%），这个上限只能通过合约升级修改。

**订单管理工具：**

| 功能 | 说明 | 谁能操作 |
|------|------|---------|
| 单笔取消 | 取消一个具体的报价 | 报价方（做市商） |
| 批量取消 | 一次取消多个报价（上限 24 笔） | 报价方 |
| 一键作废全部历史报价 | 递增 Nonce Floor，使所有旧报价失效 | 报价方 |
| 自动过期 | 报价超过有效期后自动失效，无需任何人操作 | 系统自动 |

> **什么时候用一键作废？** 行情剧烈波动时，做市商需要快速撤回所有未成交的报价。递增 Nonce 比逐笔取消更高效。

### 第五步：到期赎回

```
发行人存入赎回资金 → 持有人销毁债权凭证 → 领取本金+利息
```

**存入环节：**

1. 债券到期后，**发行人**存入赎回资金（本金 + 利息）到合约中
2. 可以分多次存入，系统会累计追踪

> **重要：** 平台链下审批流程**强制要求发行人存入全额赎回资金**（所有流通份数 × 每份赎回金额）。链上合约不限制部分存入，但平台在发债审批、认购审批及到期前的运营管理中，确保发行人有义务且有能力存入足额资金。不会出现发行人只存入部分赎回款的情况。

> 赎回资金存入后由合约保管，受负债追踪保护，**即使是管理员也无法随意提取属于持有人的赎回款**。

**领取环节：**

3. **持有人**（无论做市商或投资者）领取赎回款：
   - 系统检查：债券是否已到期、持有人是否有余额、资金是否足够
   - 系统销毁持有人的全部债权凭证
   - 系统自动计算应付金额并转账给持有人

**赎回金额计算（以上述示例为例）：**

```
每份赎回金额 = 面值 + 利息
            = 1,000 + 1,000 × 5% × (365天 / 365)
            = 1,050 USDC

各持有人赎回金额：
  做市商 A（600 份）→ 630,000 USDC
  做市商 B（110 份）→ 115,500 USDC
  投资者 A（100 份）→ 105,000 USDC
  投资者 B（190 份）→ 199,500 USDC
  合计 1,000 份     → 1,050,000 USDC
```

**代理领取：**

- 持有人可以授权一个「代理人」帮自己操作领取
- 赎回资金**始终打给持有人本人**（不会打给代理人）
- 代理人只负责触发操作，不接触资金
- 适用场景：机构用户通过运营人员统一操作

**多余资金处理：**

如果发行人多存了赎回资金（比如存了 1,100,000 但只需要 1,050,000），或有代币误转入合约：

| 场景 | 处理方式 | 何时可操作 |
|------|---------|-----------|
| 所有持有人都已赎回 | **自动释放**：系统检测到债权凭证全部销毁后，自动将多余部分解锁 | 最后一人赎回后立即生效 |
| 部分持有人尚未赎回 | **手动释放**：管理员调用释放，系统精确计算未赎回部分的实际负债，只释放已证明的超额 | 到期后随时 |
| 代币误转入（非赎回存入） | **直接救援**：管理员可直接提取（因为不在赎回负债追踪范围内） | 随时 |

> **安全保障**：无论哪种方式，系统都确保**未赎回持有人的资金不会被取走**。手动释放时，系统基于链上的「剩余债权凭证数量 × 每份赎回金额」精确计算实际负债，只释放差额。

## 四、数据可变性总览

理解哪些数据「写死了不能改」、哪些「运营中可以调整」，对业务决策至关重要：

### 永久不可变（创建后锁定）

| 数据 | 为什么不可变 |
|------|------------|
| 债券名称、代号 | 标识性信息，变更会导致混乱 |
| 面值、票息率 | 投资者决策基础，等同于合同条款 |
| 起息日、到期日 | 利息和赎回的计算依据 |
| 计息惯例、付息频率 | 利息计算规则 |
| 债券类别、ISIN | 分类和识别标准 |
| 结算币种 | 全生命周期统一使用 |
| 发行人地址 | 确保只有发行人能管理赎回 |
| 认购窗口条款（价格/额度/时间） | 创建后不可修改，错误需关闭重建 |

### 运营期间可调整

| 数据 | 谁能调整 | 说明 |
|------|---------|------|
| 白名单 | 合规管理员 | 随时增删参与者 |
| 角色分配 | 合规管理员 | 随时调整做市商/投资者标记 |
| 手续费率 | 结算管理员 | 在上限范围内调整（上限不可变） |
| 应计利息容差 | 结算管理员 | 调整链上验证的宽松度 |
| 暂停状态 | 暂停操作员 | 按环节独立暂停/恢复 |
| 结算币种策略 | 结算管理员 | 启用/禁用某个币种用于认购/结算/赎回 |
| 债券二级市场注册 | 结算管理员 | 控制某支债券是否能在二级市场交易 |

## 五、安全与风控机制

### 5.1 分域暂停

平台可以按**不同业务环节**独立暂停，而不是全盘关停：

| 可独立暂停的环节 | 暂停后的效果 | 不受影响的环节 |
|---------------|------------|-------------|
| 债券创建 | 不能创建新债券 | 已有债券的交易和赎回 |
| 一级认购 | 不能新增认购 | 已有持仓的交易和赎回 |
| 二级市场结算 | 不能成交新订单 | 一级认购和赎回 |
| 合规管理操作 | 不能修改白名单和角色 | 已有配置下的交易和赎回 |
| 赎回资金注入 | 发行人不能存入赎回资金 | 已存入资金的领取 |
| 到期领取 | 持有人不能领取赎回款 | 发行人存入资金 |

> **使用场景举例**：发现二级市场有异常交易时，只暂停「二级市场结算」，不影响正在进行的一级认购和已到期债券的赎回领取。发现合规信息有误需要紧急修正时，先暂停「合规管理操作」防止并发修改，修正完成后恢复。

> **注意**：暂停是一个开关操作，不是幂等的。已经暂停的环节再次暂停会被拒绝（防止脚本误操作），需先查询当前状态。

### 5.2 多签治理

所有重要操作由多签钱包（如 Gnosis Safe）共同确认：
- 不存在「一个人拥有所有权限」的风险
- 部署完成后，部署者的权限**自动移交**给配置的多签地址，并**选择性撤销**部署者自身权限
- 已移交给多签的角色，部署者自动放弃；部署者仍需暂时持有的角色保留并记录

### 5.3 可升级但受控

- 认购模块、结算模块和每支债券的合规模块可以升级逻辑（修复漏洞或新增功能）
- 升级后**合约地址不变**，所有持仓、余额、配置保持不变
- 升级权限由技术团队的多签钱包持有，需要多人确认
- **债权凭证本身（BondToken）不可升级**——条款锁定后不可变

### 5.4 资金保护

| 保护机制 | 说明 |
|---------|------|
| 赎回负债追踪 | 合约追踪每种结算币的赎回负债总额，管理员无法提取属于持有人的赎回款 |
| 超额自动释放 | 所有持有人赎回完毕后，多存的资金自动解锁，管理员可安全取出 |
| 手续费上限 | 管理员可以调低费率但不能超过部署时设定的上限 |
| 手续费签名锁定 | 做市商签名时锁定最高接受费率，防止签后涨费 |
| 安全转账 | 所有代币转账使用「安全模式」，转账失败则整个交易回滚，不会出现资金悬挂 |
| 原子交割 | 二级市场交易中资金和券的交换在同一笔交易完成，不可能只完成一半 |
| 重入保护 | 赎回和认购等涉及资金的操作都有重入锁，防止攻击者在一笔交易中重复领取 |

## 六、系统不负责的部分（边界说明）

| 环节 | 说明 |
|------|------|
| KYC / 客户尽职调查 | 在链下完成，链上只记录「是否通过白名单」的结果 |
| 行情展示、聊天询价 | 由前后端应用层负责，链上只处理最终的成交确认 |
| 法币入金出金 | 链上使用代币（如 USDC），法币通道由支付与托管体系完成 |
| 手续费定价策略 | 费率由平台在链上配置，但收多少是商业决策 |
| 纸质合同、司法流程 | 链下法务团队负责 |
| 债券定价、信用评级 | 链上不对债券做价值判断，定价由市场参与方自行决定 |
| 违约处理 | 如果发行人到期未存入赎回资金，链上合约不会自动追偿；违约追责属于链下法律流程 |
